# Set up the assistant computer

Use the installed `trelio-assistant` MCP surface and its discovered tool contracts.
Do not invent methods or substitute the human Trelio MCP when assistant methods
are absent. Report the exact missing runtime capability or server error.
Before the first begin, a ready user request may explicitly authorize one native
same-computer new-chat handoff when the installed/enabled plugin has no setup
tools in the current chat. Follow that request's one-hop marker and same enrollment;
do not invent that permission or repeat installation. This fallback does not apply
after the six setup/background tools are present and pairing succeeds.

The owner creates a digital assistant and starts computer enrollment from their
own Trelio profile. The ready setup prompt identifies this enrollment; it does
not authorize work. The trusted runtime creates and privately stores the verifier.
The owner reviews the exact assistant, computer and pairing code on their own
device. Do not sign the owner into Trelio on the assistant computer or copy human
OAuth, browser cookies or another computer's credentials.

Use only the runtime's protected enrollment and credential storage. Never ask for
credentials in chat or put them in commands, environment variables, clipboard,
workspace files or diagnostic output. A lost one-use exchange requires a fresh
enrollment, not replay. Hook trust and external-account sign-in remain human UI
actions; installing the plugin does not supply those approvals.

After pairing, read back `get_assistant_setup_status` with the same enrollment
and verify live assistant/device contact. If requested, install/start the background
supervisor and read its actual registration/running state. These receipts confirm
local setup in their own scope. Setup status has requiredCapabilities, not a task
pass or nextAction/continuation/workflow; its businessReady:false is not a denial
of the separately admitted background worker.

Do not wait for this setup chat to gain more tools or request another chat,
reload, reinstall or enrollment merely to obtain business methods. The facade can
notify the client of its expanded live catalogue after pairing; an unrefreshed
model catalogue alone does not establish business failure. If `get_assistant_status`
is actually exposed, use it for structural live capability read-back only. Never
call a missing tool, fabricate task-pass/proof, or borrow a human MCP.

The background runtime checks current company/model policy and task admissions,
then opens/resumes the permanent chat of an accepted task under its genuine pass
and observed hook. Actual hook admission is verified there, not by probing task
tools from setup. Codex sign-in and Hook trust remain human actions. The owner
configures company permissions, model/effort and external accounts on their own
device. Reuse existing confirmed settings; a setup catalogue gap does not mean
they are absent. An existing human connection is not transferable. Keep companies
and provider identities separate; a username alone proves no messenger identity.

When authorized and its prerequisites are configured, verify real business delivery
through that background runtime: a permitted source event reaches the durable queue, wakes
the existing task chat, produces a confirmed business outcome and an exact
receipt, and exposes the actual next recurring run. A generated file, queued
message or completed native turn alone does not prove delivery. Ordinary task
comments do not wake a chat; an actual mention of this assistant does.

Report the working capabilities and any concrete blocker. Do not enable a second
timer, make a replacement chat after uncertain provisioning, or claim unattended
readiness from installation or synthetic tests alone. Report verified pairing and
background setup separately from business conditions not yet observed.
